# Studio 0.7.130 — Chrome mouse input for ZIP downloads

The user confirmed that both `.click()` and a synthetic pointer/mouse sequence
fail on a completed ZIP, while a manual mouse click downloads immediately.
With the user's authorization, ChatGPT Bridge 1.16.11 now requires `debugger`
and uses Chrome `Input.dispatchMouseEvent` for ZIP file links and ZIP preview
Download buttons. SRT continues using its existing `.click()` path.

The bridge attaches only to the active ZIP worker tab, focuses its window,
re-resolves the file in the same response, scrolls the link into view and checks
the hit target. It sends one mouse move/press/release and detaches in `finally`.
Cancelled requests, covered controls, missing permission and debugger failures
produce errors. Preview polling does not attach unless a Download target exists.
The Chrome download listener is installed before the input; successful input is
not treated as successful download. The matching file must finish downloading.

Reload `extensions/chatgpt` as 1.16.11, allow the new permission if Chrome asks,
and refresh worker tabs. Chrome may show a debugging banner briefly. Close
DevTools on the worker tab if debugger attachment reports a conflict.
Activity should report `ZIP Chrome mouse input dispatched` followed by
`ZIP download started in Chrome` and `ZIP saved by Chrome` on success.

Validation: 126 simulated DOM, bridge and native-input tests pass, including
attachment errors, cancellation, invalid coordinates, covered controls,
detach cleanup, preview and the unchanged SRT download lifecycle. Live Windows
Chrome behavior remains to be verified by the user; this release does not claim
that `isTrusted` alone was the root cause.
